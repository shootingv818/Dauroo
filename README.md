# Dauroo — سرویس چند-مشتری ایتا

دو ربات تلگرامیِ جدا روی یک کدبیس: یکی پنل خصوصی **مالک**، یکی رباتی که
**مشتری‌ها** استارت می‌زنند.

موتور (لاگین، ارسال، ساخت مخاطب، ایمپورت تصاویر) **عیناً** از پروژه‌ی تک‌کاربره‌ی
قبلی کپی شده و دست نخورده است؛ چیزی که اضافه شده لایه‌ی چند-مشتری زیر آن است.

---

## دامنه

| مشتری می‌بیند | مالک می‌بیند |
|---|---|
| افزودن اکانت (لاگین در تلگرام) | **همه‌ی** تنظیمات |
| ارسال (تا ۳ اکانت) | کلید موتور (failover) |
| ساخت مخاطب · بروزرسانی مخاطبین | مسدود / آزادسازی |
| ایمپورت تصاویر → PDF | پیام همگانی |
| تست ارسال | ریست سه‌پله |
| تنظیم متن/فایل خودش | کارت‌های کامل خطا |
| آمار و سهمیه‌ی خودش | آمار همه‌ی مشتری‌ها + منابع سرور |

**هیچ تنظیمی در ربات مشتری نیست.** موتور، تأخیر، هم‌زمانی و سقف مرورگر همه دست
مالک است.

---

## قواعد قطعی

| موضوع | مقدار |
|---|---|
| سقف اکانت هر مشتری | ۴۰ |
| سهمیه‌ی روزانه | **۱۰ افزودن اکانت** در هر ۲۴ ساعت (غلتان) |
| سقف ارسال | **ندارد** |
| مسدودی خودکار | بیش از ۲۰ اکشن در ۶۰ ثانیه |
| مدت مسدودی | تا ابد، فقط مالک آزاد می‌کند |
| بار کاربر مسدود | **صفر** (کش حافظه، قبل از هر کوئری) |
| تایم‌اوت لاگین | ۳۲۰ ثانیه، یک متغیر واحد |
| سقف فایل | ۲۰ مگابایت |
| ارسال چند-اکانتی | حداکثر ۳ اکانت |
| زبان | همه‌ی متن‌ها فارسی |
| شماره‌ها | ماسک در پنل مشتری و گروه لاگ؛ کامل فقط پنل مالک |

**سهمیه روی افزودن اکانت است نه ارسال** — چون هر لاگین یک کروم را تا ۳۲۰ ثانیه
اشغال می‌کند، ولی ارسال با موتور سریع هیچ مرورگری مصرف نمی‌کند. ۱۰ در روز × ۴ روز
= دقیقاً سقف ۴۰ اکانت.

## راه‌اندازی

```bash
git clone https://github.com/shootingv818/Dauroo
cd Dauroo
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
playwright install chromium
cp .env.example .env      # پرش کن
```

دو پروسه، هر کدام با `MODE` خودش:

```bash
MODE=owner    python main.py     # پنل مالک
MODE=customer python main.py     # ربات مشتری
```

> اول هر دو ربات را ادمین گروه لاگ کن تا لاگ‌ها بیایند.

### چرا موتور دست نخورد

کد کپی‌شده وضعیت پنل را این‌طور می‌خواند:

```python
from bot.store import store as _store
return dict(_store.settings)
```

به‌جای ویرایش `runner.py` و `warmpath.py` و `contacts_boost/`، فایل `bot/store.py`
**همان قرارداد** را نگه می‌دارد و به دیتابیس چند-مستأجر وصلش می‌کند. هر ویژگی
داخلش وجود دارد چون یک نقطه‌ی مشخص از کد کپی‌شده صدایش می‌زند.

و اینکه تنظیمات **گلوبالِ مالک** است، میان‌بر نیست — طراحی است: در این سرویس مالک
همه‌ی پیچ‌ها را دارد و مشتری فقط محتوای خودش را.

## دو موتور

| نام | معادل فنی | ویژگی |
|---|---|---|
| **🌐 موتور مرورگر** | `bridge` | کروم باز می‌کند و از داخل وب ایتا می‌فرستد. کندتر، هر کروم ~۱ گیگ رم. **پشتیبان per-recipient دارد** |
| **⚡ موتور سریع** | `hybrid` + `browserless` | مستقیم روی HTTPS، بدون مرورگر. سریع و بدون رم. **پشتیبان ندارد** |

کلید انتخاب **فقط دست مالک** است و برای همه‌ی مشتری‌ها اعمال می‌شود — یک کلید
`failover` برای وقتی یک موتور خراب شد. سه رفتار اجباری:

1. **جاب‌های در حال اجرا با موتور خودشان تمام می‌شوند** (عوض‌کردن وسط ارسال، ریسک
   تکرار یا گم‌شدن پیام دارد).
2. **تعویض موتور مرورگرهای گرم را می‌بندد** (کلید pool شامل مسیر init-script است).
3. مقدار نامعتبر خودش به موتور مرورگر تنزل می‌کند.

⚠️ موتور سریع می‌خواهد **همه‌ی** مخاطبین یک اکانت `access_hash` داشته باشند. یک
مخاطبِ اسکرول‌شده کل مسیر سریع آن اکانت را می‌بندد — به همین دلیل پنل سه حالت نشان
می‌دهد: `⚡ آماده` · `🌐 فقط مرورگر` · `⚠️ بی‌مخاطب`. راه‌حلش یک بار
«🔄 بروزرسانی مخاطبین» است.

## لاگ و خطایابی

**یک رویداد، دو خروجی.** کارت کامل به گروه لاگ، نسخه‌ی امن به پیوی مشتری، و **کد
پیگیری یکسان** در هر دو:

```
مشتری:                          گروه لاگ:
❌ اکانت اضافه نشد               ⚠️ لاگین ناموفق
• علت: ایتا محدودیت گذاشته       • مشتری: علی · 123456789
• اقدام: ۶۰ دقیقه دیگر           • مرحله: code
                                • کد سرور: FLOOD_WAIT_3600
▪ 🔖 A3F9C1                     ▪ 🔖 A3F9C1 · 🕒 14:35
```

مشتری می‌گوید «A3F9C1 خوردم» و مالک همان را در گروه سرچ می‌کند.

مشتری **هرگز** پاسخ خام سرور، نام موتور، زمان مراحل یا آمار ناوگان را نمی‌بیند.

### جدول `events` چهار کار می‌کند
فید لاگ · شمارنده‌ی ریت‌لیمیت · سهمیه‌ی افزودن اکانت · تاریخچه‌ی هر مشتری.

عمدی است: اگر فهرست چیزهایی که لاگ می‌شود با فهرست چیزهایی که در شمارنده حساب
می‌شود فرق کند، **مسدودی قابل توضیح نیست** — می‌بینی کسی مسدود شد ولی آن ۲۰ اکشن را
در لاگ پیدا نمی‌کنی. کارت مسدودی همان اکشن‌ها را با ساعتشان فهرست می‌کند، به‌علاوه
سن حساب و تعداد اکانت — چون مسدودی دائمی است و این قضاوت تعیین می‌کند یک مشتری
واقعی از دست می‌رود یا نه.

## ریست سه‌پله

پروفایل کروم دو نوع پوشه دارد، و این تفکیک کل طراحی است:

| نوع | پوشه‌ها | حذفش |
|---|---|---|
| **کش خالص** | `Cache`, `Code Cache`, `GPUCache`, `CacheStorage`, … | فقط جا آزاد می‌کند |
| **سشن ایتا** | `IndexedDB`, `Local Storage`, `Cookies` | همه لاگ‌اوت می‌شوند |

سشن ایتا در **IndexedDB** است، پس می‌شود گیگابایت‌ها رم و دیسک آزاد کرد **بدون
اینکه کسی لاگ‌اوت شود**:

| پله | کار | لاگ‌اوت؟ |
|---|---|---|
| 🧹 **۱ — سریع** | بستن مرورگرها + حذف کش | ❌ |
| 🗂 **۲ — عمیق** | + کپچرهای قدیمی، PDFها، رویدادهای قدیمی | ❌ |
| 🔴 **۳ — کامل** | حذف واقعی اکانت‌ها، **با تأیید تایپی** | ✅ |

پله ۲ **جدیدترین** کپچر هر اکانت را نگه می‌دارد، وگرنه موتور سریع خلع سلاح می‌شود.

و یک **نگهبان شبانه** هر شب ساعت ۳ خودکار پله ۱ را می‌زند، تا معمولاً لازم نشود
دستی این دکمه را بزنی.

## پروفایل نیمه‌ساخته

لاگین **داخل مرورگر** انجام می‌شود و کروم پوشه‌ی پروفایل را هنگام باز شدن می‌سازد،
پس «فقط بعد از لاگین موفق بساز» مستقیماً ممکن نیست. راه‌حل:

```
۱. لاگین با نام موقت:  _pending_<شماره>_<رندوم>
۲. موفق؟   →  rename به کلید واقعی   (اتمی، همان فایل‌سیستم)
۳. ناموفق / تایم‌اوت؟  →  کامل پاک
```

به‌علاوه یک جاروی بوت که `_pending_*`های مانده از کرش را پاک می‌کند.

## کلید اکانت

کلیدی که به موتور داده می‌شود **`accounts.id`** است، نه شماره — و
`accounts.phone` یکتاییِ `(customer_id, phone)` دارد، نه یکتاییِ سراسری.

دو مشتری می‌توانند به‌درستی یک شماره را اضافه کنند؛ اگر کلید شماره بود، سشن، اجاره‌ی
pool و قفل‌های آن دو با هم تصادم می‌کردند.
